# Обновление GymKeeper на программу 3.0

## Важное

Это обновлённые исходники из предоставленного ZIP. Репозиторий GitHub и рабочая база пользователя автоматически не изменялись. Публикацию и миграции нужно выполнить отдельно. Не пересоздавайте базу и не удаляйте историю.

### 1. Сохранить данные до обновления

1. Откройте старое приложение с сетью и дождитесь синхронизации офлайн-очереди.
2. Завершите или осознанно отмените активную тренировку. Отмена удаляет только её записи.
3. В настройках скачайте полный JSON-backup. Дополнительно сделайте резервную копию PostgreSQL на стороне хостинга.
4. Сохраните текущий коммит приложения и параметры деплоя. Не вставляйте секреты в чат или Git.

Новая версия не очищает старые локальные кэши и очередь автоматически. Но экспорт сервера не включает ещё не отправленные данные браузера — поэтому шаг синхронизации важен.

### 2. Обновить файлы в отдельной ветке

```sh
git checkout -b program-3-0
```

Скопируйте содержимое папки проекта из архива поверх рабочей копии репозитория. Сохраняйте собственные `.env*` и папку `.git`; в архив они не включены. Проверьте diff. Если репозиторий менялся после предоставленного ZIP, переносите изменения через сравнение, не затирайте более новые правки.

### 3. Проверить на тестовом окружении

```sh
npm ci
npm run lint
npm test
npm run program:verify
npm run typecheck
npm run db:dry-run
npm run build
```

В среде подготовки удалось выполнить unit-тесты, проверку нового вычислительного ядра и синтаксиса; полная установка зависимостей, Next.js build и PGlite dry-run были недоступны. Поэтому эти шаги обязательны перед деплоем, а не считаются уже пройденными.

На копии базы отдельно проверьте: существующую историю, незавершённую старую сессию, остаток локальной очереди, восстановление старого JSON-backup, текущий день, R и даты.

### 4. Применить миграции

Сначала на тестовой базе, затем на рабочей после резервирования и проверки:

```sh
npm run db:migrate
```

Используйте правильный `DATABASE_URL` в приватном окружении. Команда применяет ещё не записанные миграции по порядку.

- **015** добавляет индивидуальный профиль и журнал выполнения поддержки. Никакой медицинский уровень из старой версии не конвертируется в новое разрешение.
- **016** добавляет отдельные циклы, занятия и упражнения `v4:` и переключает активную версию. Старые `v3:/v2:/v1` и связи фактических подходов остаются.
- Значения R, текущего дня и календарных дат не сбрасываются.
- Снимок плана новой сессии хранится отдельно от сегодняшних настроек. Подтверждённое снижение ИИ-тренера сохраняется как дополнительный вариант; исходный снимок остаётся.

Проверка после миграции: новая программа имеет **22 цикла, 88 карточек дней и 44 силовых занятия**. День 171 — полный тренировочный отдых, не новая кардио-сессия.

### 5. Настроить индивидуальный режим

В настройках подтвердите только действительно уточнённые ограничения, введите рабочую базу R, фиксированный предел C (если он задан), шаг штанги и массу грифа. Пустое поле C не означает допуск к максимуму. Старый R сохраняется, но его достоверность не подтверждается автоматически.

Без исходных данных контроль выполняется как ознакомительная тройка около RPE 6–7. Индекс T/0,863 не становится новой рабочей базой автоматически. Поддержка и ноги выключены по умолчанию; включать их нужно отдельно.

Ветка 1ПМ выбирается до Ц17 и подтверждается в Ц20. Подготовка проверяется по реально записанным новым синглам; старые галочки не являются доказательством подготовки. Офлайн новые КТ и ветка 1ПМ не запускаются.

### 6. Опубликовать

После успешной проверки:

```sh
git add .
git commit -m "Transfer training program revision 3.0"
git push -u origin program-3-0
```

Создайте pull request и проверьте preview-деплой, затем обновите основное приложение обычным способом. Этот архив не выполняет push, merge или production-деплой сам.

## Поведение истории и офлайна

- Архивная активная сессия доступна для завершения/отмены, но не для новой нагрузки по старым подсказкам.
- Новая офлайн-сессия хранит собственные R, профиль и подготовленный план. Для нового старта нужен актуальный кэш; после недели его требуется обновить с сетью.
- Очередь удаляет только подтверждённые идентификаторы операций, а не первые N записей.
- Уже выполненный некорректный офлайн-подход сохраняется как факт и помечает нарушение; это не разрешение продолжать нагрузку.
- Историческая автоматическая прогрессия офлайн намеренно консервативна: нет серверного подтверждения двух сопоставимых выполнений.
- При восстановлении старого backup актуальная программа добавляется повторно внутри транзакции, даже если её миграция уже значится выполненной. Этот сценарий всё равно нужно проверить на копии вашей базы.

## Откат

До применения миграций можно откатить файлы к сохранённому коммиту. После записи новых тренировок не восстанавливайте старую базу поверх новых данных без экспорта. Добавленные таблицы/колонки и `v4:` не удаляйте вручную; подготовьте отдельный план отката и сохраните новые записи.
